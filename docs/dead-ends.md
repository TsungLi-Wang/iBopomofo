## A. 誤診（浪費最多時間的一類）

## B. 量測方法（同一個錯誤換皮出現過五次）

**共通病根：在 A 分布上歸納出來的判準，拿到 B 分布上用。** 五次都是這個。

- **用 EX1166 歸納規則／挑參數，再用 EX1166 報成績。** EX1166 是 grok 生成的，
  規則也歸納自它 —— 同一個模型自我驗證。救 134 壞 1 → 真實語料救 3 壞 27。
  **鐵則：驗證來源 ≠ 機制來源。** 證據：本檔 C 節前兩條。

- **同一份資料選參數又報成績。** 掃六個 alpha 挑最高的報出來 →「五組進步 +5.6」，
  換乾淨做法變成「四進兩退 +1，跟零分不開」。同一機制數字差三倍。

- **`b=0` 不等於「證明無害」。** 的／得警察 v0 在 MAIN 上 `b=0 c=4`，因為四條規則有三條
  在 MAIN 裡**根本沒有反例可以證偽**。換沒看過的句子一打，15 句誤殺 8 句。
  → **新規則必須自帶反例考卷**（gold＝「不該改」的句子）。

- **逐組報小樣本百分比。** 44 題裡的「+9.1 分」＝多對 4 題，誤差 ±十幾個百分點。
  → 報百分比一律附分子分母；分母 < 100 不下結論。

- **隨機抽樣送人判語料乾淨度。** `的得` 抽 200 句有 188 句是「的」，
  回報「97.5% 乾淨」—— 那 188 句全是送分題。→ 只能 (a) 在文法真的決定答案的構式上直接數
  n-gram，或 (b) 對**低頻字那一側**分層抽樣。

- **拿題庫的三字窗／出貨規則當標準答案量語料。** 題庫刻意收「窗口看不出答案」的難題，
  規則是在「這位置是難題」前提下歸納的；套到通用語料就把合法寫法算成寫錯
  （「你_說」誤報 1755 次、「你在幹嘛」誤報 17,893 次）。

- **舊北極星 tw538（537 句）已作廢，不得再當 gate。** 鑑別度掉光：要量的進步比它自己的
  噪音還小，而且一直拿全部題目調模型＝背考古題。`walk ON 333`／`v2c 387` 只當歷史。

## C. 選字機制（做過、退版過）

- **六組同音字歸納規則（70 條，v2.16.0/1 → 2026-08-11 退版）。** EX1166 救 134 壞 1；
  PTT 救 3 壞 8；X 救 0 壞 19。實際災情：前女友→錢女友、都在找→都再找、結婚吧→結婚巴。
  規則表存 `Source/Engine/eval/artifacts/homophone-rules-failed.tsv`；
  **引擎 `ParticleRuleDisambiguator` 本身沒問題**，失敗的是規則內容與產生方式。

- **同音頻率先驗壓縮（路線 A，`confusion-alphas.tsv`）。** 壓哪些讀音是在 EX1166 上挑的；
  兩份真實語料逐讀音重測，四個讀音全部淨傷害或在雜訊內 → 條目已清空（機制留著）。
  要重啟任何讀音：先在真實語料證明淨正向，再看 EX1166。

- **拿自然文本修剪規則。** 用一半找「淨傷害」的 6 條剪掉、另一半報成績 → **兩份都變差**
  （自然 88.1→87.6、EX1166 68.8→67.5）。那 6 條是從 800 題裡 9 次淨傷害挑的，挑到雜訊。

- **EX1166-only 當新組 v2d 訓練源（棒② NO-GO）。** 較叫 b=7 c=0（MAIN 92.3%→87.7%）、
  全尺 p_harm=0.035 顯著淨傷害、EX1166 train↑ heldout↓。**v2d 訓練源必須與 MAIN 切開。**

- **舊的 在／再 混淆表（`confusion-pairs.tsv`，v2.7.0 刪除）。** 取回實測 93% → 90.25%。
  它是 v2c 成為主力前訓的（913 句合成語料），現在會跟 v2c 搶決定。**七月那次刪除是對的。**

- **補 v2c 的視野死角。** 400 題只有 **1.2%** 是「正解沒進十條候選」；真正的錯（23/28）
  是「看到了還選錯」。天花板太低，不值得做。（issue #4）

- **五組一起做對比訓練。** 只有在／再顯著（+18），其他四組改對改壞各半、純洗牌。
  改成只解凍在／再後其他組 0 改變，出手準確率 55%→95%。**要加新組就一組一模型獨立驗。**

- **作做坐座 v2d（2026-08-13 棒⑩ NO-GO）。** 語料挖掘＋難例挖掘訓的模型，
  對出貨 v2d 逐題配對：PTT **救 20 壞 56（淨 −36，p=4.4e-05）**、
  X **救 2 壞 8**。訓練當下語料 dev 就已經 82.4%→81.5% 變差。
  原因是先驗的：這組路徑層天花板只有 71.1%，而它最大宗的錯是「上下文不足」
  與「整句解碼」，對比訓練打的是第三大宗。**別再訓這組。** 證據：issue #9。

- **節點層神經專家對作做坐座（2026-08-14 棒⑬ NO-GO）。** 2.6M 參數的封閉集合打分器，
  在 walk 節點既有候選裡改選、預設棄權、只開 ㄗㄨㄛˋ 一組。dev 出手精準率 0.630，
  兩份真實語料卻是 **自然 救10壞38（淨 −28，p=9.7e-05）、X 救1壞6**。
  **圍堵有效**（只改 62 句、目標外 5 句、整句正確率只掉 0.04 個百分點、延遲 +0.15ms/句），
  壞的是模型不是接法。證據：`docs/decisions/0008`。

- **節點層專家的 training recipe 修正（2026-08-14→17 棒⑭-B，仍 NO-GO）。**
  淘汰 hard ×12 物理複製、改逐樣本 loss 權重之後：自然 −28→**−10**（p 0.26）、
  X −5→**+2**、整句逐字正確率 −31 字→−9 字。**方向對了，但還是沒過。**
  三件量出來的事：① 移除 ×12 是最大的一刀；② **單字節點加權反而更差**
  （移除 ×12 後單字已佔 64.6% loss，再加權推到 78.5% 就過度保守）；
  ③ 方向有界配平沒有額外收益。證據：`analysis/node-expert-recipe-experiments.md`。

- **拿「零傷害」的點估計當進場依據（同上那次的方法錯）。**
  audited dev 在 τ=0.5 觀察到 27 次出手、**0 次改壞**，據此預估淨 +19.9／1,000；
  正式測試量到真實傷害率 **3.4%**、淨 −10。可判定的「引擎本來就對」只有 127 個節點，
  在 3.4% 下觀察到 0 次改壞的機率約 1.3%。
  → **dev 的零傷害要看區間上界（這裡約 2.4%），不是點估計**；
  凍結規則應該是「預估淨值的 95% 下界 > 0」。用那條，這次事前就會被擋下來。

- **稀有方向的節點不夠同時餵 dev 與 training（2026-08-18 棒⑭-D PART C）。**
  新 audited dev 為了取得量測 power，把 `做→X` 幾乎抽光：母體 199 → **可訓練 1**；
  `坐→坐` 90 → **0**、`作→坐` 24 → **0**。同配置的對照組 R4′（只差排除清單從
  193 份變 684 份）因此把坐全部推走：`坐→坐` damage **2/71 → 67/107（62.6%）**、
  加權 net +0.98% → −3.89%。
  **在解決這個資源衝突之前，同一份語料上的 recipe 比較都會被它污染。**
  證據：`analysis/node-expert-failure-mode-training.md`。

- **子群條件式抑制 `作→作·單字`（2026-08-18 棒⑭-G，NO-GO）。**
  只對「引擎選對 ∧ 單字 ∧ 目標字＝作」這 81 筆（train 的 0.09%）加 margin penalty。
  damage 確實降（15.3%→5.1%／0.7%），但 **`作→做` rescue 也被壓掉 70–78%**
  （23→7／5）。範圍沒寫寬（`做→坐` 幾乎不受影響，8/4→7/4→4/3），
  **是子群本身在特徵上不可分**：`作→作·單` vs `作→X·單` 的 R4 margin
  **AUC 只有 0.615**，引擎側特徵（候選數 13、u(engine) −2.76、PMI 0/0、句長）
  完全相同。→ 瓶頸是**表徵**不是配方；要突破得動特徵集或架構，需另外立案。

- **拿 margin hinge 壓 damage（同上那次，NO-GO）。** 部署規則是
  `score(best)−score(engine)>τ`，而 cross-entropy 對這個差值沒有壓力，
  所以加 hinge 要求引擎選對時領先次高 m。damage 確實壓下去
  （作→作·單字 57.9%→0%），但**它學到的是「全部都別動」而不是「這一格別動」**：
  margin 中位數全面塌到 0，連原本做得最好的 `作→做`（rescue 94%）也歸零，
  加權 rescue 26.1%→1.7%。**damage ↓ 但 rescue ↓↓，不接受。**

- **audited dev 只按「方向」分層，沒按「節點跨度」分層（2026-08-17 棒⑭-C 查出）。**
  12 個 X→Y 方向的覆蓋其實是完整的，`做→坐` 也有 18 個樣本 —— 漏掉的是**結構子群**：
  `作→作` 在 dev 只有 6.7% 是單字節點（2 個），測試集是 33.1%（53 個）。
  而 **37 次改壞裡有 34 次（92%）發生在單字節點**，傷害率 10.06%。
  dev 那一側只有 36 個單字節點、觀察到 0 次，Wilson 上界 9.64% ——
  **在數學上就偵測不到 10% 的傷害率**。
  → 分層要加第三軸（engine choice × 方向 × 跨度），每個對角線單字格至少 120 筆。
  → **整體單字佔比 dev 54.4% vs test 54.7% 看起來沒問題**，問題只在逐格看得到。

- **把「模型不出手」當成沒事（同上那次）。** `做→坐` 是 Natural 最大宗的錯（73 個），
  R4 在 dev 與 test 上都只出手 2 次，margin 四分位全是 0.00 ——
  它的 argmax 就是引擎已選的「做」，**不是被 τ 擋住，是根本不認為該改**。
  dev 忠實報告了這件事，是我沒把它當一回事。凡引擎選「做」的錯，模型一律不動。

- **audited dev 的規模要按「模型會出手的引擎正確節點數」算，不是按總題數。**
  263 題聽起來夠，但在 τ=0.5 只換到 27 次出手、127 個引擎正確節點 ——
  分辨不出 0% 與 3% 的傷害率，而那個差別就是 GO 與 NO-GO 的差別。

- **難例只按「引擎選錯」挑，不按方向配平（同上那次量到的根因）。**
  難例集被「引擎過度偏好『作』」單一方向主導，×12 加權後模型學到的是
  「往『作』的反方向推」而不是判別 —— 把本來對的「坐等」「坐辦公室」通通推走。
  改壞的 38 個裡有 10 個是把對的「坐」推走。**要按 (引擎選 X → 金標 Y) 逐方向配平。**

- **拿未經人工核的 PTT 原文當 dev 去定門檻（同上那次量到）。**
  dev 出手精準率 0.630 → 人工稽核過的真實語料 0.161。同一個領域、不同的標籤品質，
  門檻就轉移不過去。→ 門檻要嘛在人工核過的資料上定，要嘛承認那個 dev 只是煙霧。

- **⚠️ 新增同音組時從 v2c 起訓（同上那次踩到）。** 會把 v2d 的在再微調整個丟掉
  —— 上面那次量到的「在再 救14壞17」就是這樣來的，不是訓練污染。
  **要從 `path-char-lstm-spoken-v2d.bin` 起訓**，每加一組都疊在前一組上。

- **`ship-gate.sh` 不能拿來判「換模型有沒有效」。** 它比的是「規則開 vs 規則關」，
  兩邊用同一個 `path-char-lstm.bin`。棒⑩ 那個淨傷害的模型照樣跑出
  `SHIP_GATE_STATUS=CORE`（數字還跟 v2.17.0 一模一樣）。
  換權重要用模型對模型的逐題配對（McNemar），CORE 只是出貨的必要條件。

- **拿隨機語料句或「難例挖掘」訓 v2d。** 15.5 萬隨機句＝沒學到（送分題）；
  8,762 挖掘難例＝封存集 −12。3,262 題的 EX1166 train 反而 +16。
  **決定成敗的是訓練資料的分布，不是量也不是乾淨度。**

## D. 「的／得」（兩個獨立死因，整組別碰路線 C）

- **神經模型解不了。** 拿掉詞頻優勢只問 v2c 哪句順：59 句 66%，該打「得」的只對 9/29，
  錯的全選「的」。根因＝v2c 的 PTT 訓練語料本身四成寫錯
  （程度副詞「跑得很快」：得 22,940 vs 的 35,099 → **39.5% 正確**）。（issue #1）

- **程度副詞半邊（得很／得超／得太）五種寫法都試過，誤改率地板 20%。**
  「你說的超展開」跟「你說得很誇張」在前後三字內完全同形。（issue #2）

- **架構上也到頂。** 路徑層天花板 62.1%，規則層已經把它推到 63.3% —— **比天花板還高**。
  就算給完美訓練資料，重訓 v2c 也修不了：正解那條路徑擠不進 N-best。
  **那組只有節點層機制（規則／未來的神經專家）有效。**

## E. 架構層（顧問最常提、真的試過的）

- **加大模型／加大詞庫／換通用 LM 架構／上 LLM。** 全在死亡名單：fusion 調參（≤+1）、
  池擴張、詞庫增補（B 類 0 缺字）、純 LSTM scaling、通用 LM 架構替換（ppl 好分數爛）、
  單點翻字訓通用判別器（held-out 全負、延遲 30×）、通用 instruct LLM 當判別天花板
  （75.6%，遠低於 96% 門檻）。**這是「同音消歧」問題，不是「語言生成」問題。**

- **當專家的提案聽起來很厲害，先確認它是不是在描述已經存在的東西。**
  「要做詞級、用 n-gram」正是 walk 引擎本來就在做的（詞圖 lattice＋Viterbi＋bigram）。
  能撿的珠子撿；要重寫引擎／DB 的部分堅決擋掉。

- **神經消歧專家要接在「節點的候選清單」上，不能接在「N-best 路徑」上。**
  Oracle：路徑層 85.3%、節點層 95.9%。接線位置已存在並驗證過
  （`ParticleRuleDisambiguator` 的 `selectOverrideUnigram`）。

- **四成三的錯誤不是選字問題。** EX1166 封存集 510 個錯裡 220 個（43.1%）是整句解碼錯，
  目標字只是被連坐。路線 A／B／C 做得再好都修不到。工具：
  `Source/Engine/eval/benchmarks/error_taxonomy.py`。

## F. 工程／CI

- **把 `whisper-server` 提交進 git。** 3.5MB 二進位進公開 repo：歷史不可逆膨脹、
  審查看不出 diff、綁 CPU 架構。維持每次重編（公開 repo 的 Actions 免費）。

- **CI 快取 whisper。** 換版忘改 key 會造成「假綠燈」，比紅燈危險。

- **ship-gate 在 CI 只能 SUBSET，永遠不可能 FULL。** 兩份真實語料在
  `~/Documents/i注音-語料/`，隱私紅線不可上傳，runner 讀不到。
  **CI 全綠 ≠ 可發版** —— 那正是 v2.16.0／2.16.1 退版兩次的病根。

- **⛔ 禁止為 E2E／輸入法切換蠻幹（Johnny 2026-08-12 明令）。** 關卡 1＋2 是離線的，
  **不需要**選對輸入法；關卡 3 預設不跑（`SHIP_GATE_E2E=0`）。選不到 i注音、出英文鍵序
  ＝ harness 環境問題，**一次失敗就停**，不准重試多輪「修好切換」。

- **別把要留的東西放 `/tmp`。** 重開機清光。踩過三次，其中一次是 `ship-gate.sh` 的評分機
  本體不見，出貨關卡直接跑不起來。→ `./scripts/build-eval.sh` 重建。

- **重裝輸入法別 `rm -rf` 再放。** 會被踢出選單列。就地 `ditto` 覆蓋。

- **背景程序不能自己啟用輸入法。** `TISEnableInputSource` 對已從清單移除的來源回 `-50`，
  一定要人在系統設定按。已啟用的來源之間切換則可以。
