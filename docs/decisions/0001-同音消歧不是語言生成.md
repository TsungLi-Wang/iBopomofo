# 0001 — 這是同音消歧問題，不是語言生成問題

**決定**：i注音 的命題只有一句 —— 使用者打注音，系統要在**合法同音字／詞**裡挑出
**這個語境下對的那一個**。不是寫作文、不是接話、不是讓大模型自由發揮。

這句話是整個專案的定盤星。

## 為什麼

使用者最基本、最在意的就是「字打對」。而「字打對」是**判別**問題：候選集合是封閉的
（讀音決定），要的是在候選裡做對選擇的判斷力，不是產生語言的能力。

兩者要的東西完全不同。判別問題的瓶頸在**判斷力**，不在候選生成，也不在模型規模：

- Oracle 量法：就算給引擎完美選位、再加 v2c，也只到 +15，離「完美判別器」天花板很遠。
  **這個結論不依賴任何考卷的鑑別度**，所以它站得住。
- 候選層幾乎沒有空間：實測 400 題只有 **1.2%** 是「正確答案沒進十條候選」。
  真正的錯（23/28）是「看到了還選錯」。

含意：加大模型、加大詞庫、換架構都救不動 —— 那些方向全部試過並失敗，見
[`docs/dead-ends.md`](../dead-ends.md) E 節。

## 你會反覆遇到的兩種誤導

1. **「換更強的語言模型／加大詞庫／上 LLM」。** 聽起來永遠很有道理，幾乎永遠是走錯軸。
   通用 instruct LLM 當判別天花板實測只有 75.6%，遠低於 96% 的門檻。

2. **「要做詞級、用 n-gram、今天是 >> 今天事」。** 這**正是** McBopomofo 現有 walk 引擎
   本來就在做的（詞圖 lattice ＋ Viterbi ＋ 詞庫 bigram 情境）。這類提案的例子全是
   「頻率一面倒」的易解案，引擎早就對。真正卡住的是「兩條詞路都合理、頻率分不開」的難案
   （權力／權利）。

   → **當專家的提案聽起來很厲害，先確認它是不是在描述已經存在的東西。**
   能撿的珠子撿（把詞級混淆對加進考卷）；要重寫引擎／DB 的部分堅決擋掉 ——
   那是重建已存在的東西，高風險零上檔。

## 這個決定怎麼落到架構上

錯誤分層表（`Source/Engine/eval/benchmarks/error_taxonomy.py`）說：剩下的錯裡
四成三是**整句解碼錯**，目標字只是被連坐；真正屬於排序的約四成。
而 oracle 說路徑層天花板 85.3%、節點層 95.9%。

→ **未來要做神經消歧專家（「中文警察」），必須接在「節點的候選清單」上，
不能接在「N-best 路徑」上。** 接線位置已經存在並驗證過：`ParticleRuleDisambiguator`
用 `selectOverrideUnigram` 就是那個位置。

## 什麼會推翻它

只有一種：出現證據顯示**候選生成層**（而非排序層）才是主要瓶頸。目前的量測（1.2% 死角、
節點層 oracle 95.9%）指向相反方向，而且量了不只一次。
