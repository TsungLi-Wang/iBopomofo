## 8. 為什麼是這條

A 與 B **不該分兩次做**。兩者共用同一個成本 —— 一次 build＋安裝＋兩到三週 dogfood。
分開做要付兩次那個成本，而 B 的程式碼量小到不值得為它另開一棒。合併後：

* 有真實產品問題（我們不知道使用者在改什麼）
* 可觀測（⑲ 的碼已寫好且測過）
* 介入點明確（發版；分母是 commit 路徑上的單一 hook）
* 最小 prototype 極小（安裝 ＋ 約 60 行）
* 可以 replay（`build_product_benchmark.py` 已存在）
* 可以算 rescue／damage／net（**有了 B 才可以**）
* 成功後直接接上產品（第一版 Product Error Map → 決定下一個真正的研究題）

而且它**不含任何選字行為變更**，Damage 風險結構性為零。

## 9. 為什麼不是另外兩個

**C（動 LM）WAIT。** 唯一最重要的 missing evidence：
> **那 87.6% 的真實修正，錯誤分布長什麼樣、集不集中。**

它不是「還要再研究一下」，它是**會直接改變 GO／DROP 的那一個未知**：
若真實錯誤集中在少數幾類，該做的是針對性介入（成本低得多）；
若像目前 n=15 暗示的那樣完全長尾，那 C 的大工程才有理由，
而且要在**真實分布**上重新定義成功條件。A＋B 正好產出這份證據。

**SEI WAIT。** 它的整條推論鏈第一步就過不了：

```
Decision Census 是否可行？ → 目前 NO（見第 11 節）
是否存在集中性的高-risk decision？ → 無法回答，沒有分母
是否可以可靠預測？ → 不能問，前一題沒答案
```

**現在不要訓 SEI 模型。** 它最小需要補的 evidence 就是 A＋B 的產出。
另外要提醒：⑭-N 已經量到「條件 AUC 0.459，低於隨機」——
「預測這一個決策是不是錯的」這件事在節點層已經失敗過一次。
SEI 若要重開，必須先回答它跟 ⑭-N 差在哪。

**這兩個 WAIT 不是暫緩敷衍**：它們共用同一個解鎖條件，而那個條件正是 GO 的那條路的產出。

## 10. 最小可驗證實驗（MVE）

分兩件，**同一個 build 出貨**。

### MVE-1：把 ⑲ 的儀器裝上（分子）

* 動作：從 `baton13-node-homophone` 建 build → `./scripts/ship-gate.sh` → 就地 `ditto` 覆蓋安裝
  （**不可 `rm -rf` 再放**，會被踢出選單列 —— `dead-ends` F 節）。
* 改 production 行為：**無**。⑲ 的新增碼全部只讀。
* 驗收：安裝後 `strings` 搜得到 `TRUE_CORRECTION`；實機打幾句、故意選錯再改，
  log 出現 `NF==10` 且 `event_type=TRUE_CORRECTION`、`engine_choice` 非空。

### MVE-2：分母計數器（Decision Census）

**唯一缺的欄位是「使用者沒有出手的那些決策」。** 缺的原因是結構性的：
log 只在修正時寫入。最小補法：

* 新檔（`Source/` 下的 DecisionCensusLog.swift，**本棒未建立**）：**純計數、零文字**
  `1 \t ISO8601 \t n_nodes \t n_chars`，共用 `ManualCorrectionLog` 那個已修好的 fail-open writer，
  寫到 `~/Library/Application Support/iBopomofo/decision-census.log`。
* 介入點：`Source/KeyHandler.mm` 已有現成的單一 hook ——
  `_lastHardCommitShadowUnits = [self snapshotCharacterShadowUnits];`
  出現在三處（`hardCommitSentence`、`handleForceCommit`、L1646），
  都正好是「組字區即將送出」。在同三處加一行 `[self logDecisionCensusAtCommit]`。
* **刻意不做**：不呼叫 `candidatesAt()` 逐節點判斷「有沒有歧義」。
  那會在 commit 路徑上加 O(n) 次 lattice 查詢。
  歧義度可以事後從修正事件的 `candidate_count` 補回來，不必在打字當下算。
* 分子 ⊂ 分母：composing 路徑的修正發生在 commit 之前、reselect 在之後，
  兩者修正的節點都會被同一次 commit 計到。母體一致。
* 隱私：**不含任何文字**，收集範圍嚴格小於現況。沿用既有
  `Preferences.enableManualCorrectionLog` 開關，不新增偏好、不上傳。
* 測試（`McBopomofoTests/` 下的 DecisionCensusLogTests.swift，**本棒未建立**）：純函式行格式、
  schema 可辨識（欄位數 4，與 correction log 分檔故不相撞）、空 walk 不寫、偏好關閉不寫。
* 同時修 **D3**：`scripts/correction-census.sh` 補 v2 分派，並讀入分母檔算出修正率。

## 11. 成功條件

MVE 本身的成功條件（**不是**模型指標）：

1. 安裝後 7 天內，log 出現 **≥ 100 筆 `NF==10` 事件**，其中 `engine_choice` 非空 ≥ 95%。
2. `decision-census.log` 的 commit 數 > 0 且逐日單調累積。
3. `build_product_benchmark.py` 能把兩個檔合併算出 **修正率 ＝ TRUE_CORRECTION ／ 總 node decisions**，
   而且這個數字有分子有分母、可以寫進報告。
4. 累積到 **≥ 300 筆 TRUE_CORRECTION 或滿 21 天（先到者為準）** 時，產出第一版
   **Product Error Map**：`engine_choice → user_choice` 配對分布、`candidate_count` 分布、
   錯誤集中度（前 10 配對覆蓋率）、單字 vs 詞級、讀音分布。
   **一律附分子分母；分母 < 100 的切面不下結論。**
5. **Error Map 不得預設錯誤類型。** 不准先寫「我們應該研究在／再」——
   由觀察到的分布決定第一個值得研究的錯誤類別。

## 12. 失敗／停止條件

* **打字延遲或穩定度退步** → 立刻退回舊 build，MVE-2 判 DROP。這是唯一的硬紅線。
* 安裝 7 天後 v2 事件 **< 20 筆** → 表示 D2 那個 40／天推估錯了，停下來重查寫入路徑，不要繼續等。
* 滿 21 天且 `TRUE_CORRECTION` < 100 → **不要再換一種記錄方式**。
  回頭檢討 [`0003`](0003-真人校正是下一階段的燃料.md) 那個賭注本身。
* Error Map 若顯示錯誤**完全長尾**（前 10 配對覆蓋 < 10%）→ **SEI 直接 DROP**，
  不需要再做可行性研究；同時 C 的成功條件要在真實分布上重寫。
